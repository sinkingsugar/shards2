## 2026-10-05-7c974be-claude-929d96#F1
- Disposition: fixed (implementation claim, awaiting independent verification).
- Change/reason: Seq.Make and Table.Make return to unit state and retain no last output. Their generic leaf implementations return newly owned collections. The shared builtin executor also recognizes constructor segments: it consumes the incoming value, recovers uniquely owned Vec/BTreeMap storage with `Arc::try_unwrap`, and reuses the owned buffer across consecutive constructors. Shared inputs are never mutated or copied just to reclaim their storage. The output is wrapped in an Arc only at a boundary. Table entries are sorted at compose selection, and key layouts are checked/rebuilt when shapes change. No output buffer or captured element survives in constructor state. The new constructor path is safe Rust; both schedulers use it.
- Checks/ownership contract: checking builds validate each intermediate output. The constructor group contains no arbitrary callbacks or frame writes. Ownership moves with the current pipeline output; ordinary output consumption releases captured values. Generic shard APIs and numerical scratch/SIMD behavior are unchanged.
- Regression evidence: shared `discarded_sequence_constructor_releases_captured_values` and `discarded_table_constructor_releases_captured_values` compare Arc owner counts before execution and after Count consumes the constructor output, while paused with the instance still alive. They cover captured sequences, strings and tables. The initial negative control, before the new constructor executor was added, ran the new tests against the original cached implementation: all four native cases failed with three owners rather than two. With this fix all pass on both native schedulers and stackless WASI.
- Additional evidence: `collection_outputs_keep_saved_snapshots` still passes; new `constructor_segments_preserve_snapshots_and_change_table_shapes` covers shared outputs, different source key orders and key-set changes on both schedulers. The unit test `constructor_reuses_unique_sequence_storage_but_preserves_shared_input` verifies actual Vec allocation reuse and preservation of shared input. All inline executor tests pass Miri.
- Performance evidence: the complete matched 25-workload suite was rerun with the documented four widths and nine retained samples per engine/cell. All values/counts passed. Constructor execution improved relative to the previous Rust build while Add remained near or faster than 1.x on the measured chains. The review's growing-accumulator scripts were rerun before/after with both shapes and schedulers, 10,000/40,000 iterations and three alternating process rounds; all final counts matched. The quadratic regression disappeared in these measurements. Exact results, source/binary hashes, script text and commands are in the [report](../../docs/vm-execution-benchmarks.md#constructor-retention-review-follow-up) and [committed data](../../bench/vm-execution/results/2026-10-05-owned-constructors/).
- Limits: construction still exceeds the 2× target versus 1.x. Whole-process retention timings include startup/parsing; the deterministic ownership regressions guard the reference-retention cause. Reuse applies to consumed input and consecutive constructor runs, not arbitrary subsequent invocations. The review's pre-existing passthrough-retention note (ExpectSeq/Log) is outside F1 and was not claimed fixed. No independent verification is claimed by this resolution.
