## What was wrong

The benchmark paragraph of the corrected record compared two builds that both predated the fixes. The shell's `CARGO_TARGET_DIR` sent the release build of d2c26ee to another directory, and the "new" binaries copied from `target/release` were an earlier build (no string unique to the fixed code is present in them). The claim "no runtime-path change was measurable" therefore had no evidence behind it.

## What the fixed code actually measures

This Mac, release, default build profile, interleaved with 0156b791e925d910f17d5ada5acd94a2f0fecc16 binaries; each binary was checked for a string only the fixed code contains.

- **d2c26ee as committed:** `bench_instances 1000` 89.6 against 87.8 µs per tick (12 alternating rounds each, non-overlapping distributions): a 2 percent regression. Cause: the exit-time release of a kept frame's locals looked the frame up again at the call site, one arena lookup per call, and the entity workload makes one framed call per tick.
- **b6a8946 (this snapshot):** the release happens in the frame's own completion, where every exit of an invocation passes with the frame in hand. A flow's hidden slots are released only when it ends abnormally. Result: entity 89.09 against 89.20 µs (16 rounds each), 90.28 against 90.23 in an earlier 24-round batch; heap 1.30 KiB per instance on both. `bench_depth --progress` 35.6/38.1/38.1/39.1 against 35.9/38.2/38.4/39.0 ns. The matched VM suite (cases do-int, add-int, add-float, add-float4, take-seq, take-table, get-seq, update-seq, push-shared-seq, make-seq, make-table; widths 0 to 256) is at parity from width 8 up, except `add-float`, 25 percent faster (61 against 77 ns at width 64).
- **Open:** the fixed cost per iteration (width 0) reads 0.25 ns higher, 4.75 against 4.5 ns (1.x: 5.2), for loops whose compiled instructions are identical in both builds (checked: `loop-test`, `get-local-drop`, `set`, `inc`, `jump`, no `clear`). The dispatch block of `inline::run` is byte-identical at the same offset; the new `Op::Clear` arm changes block order and register choice elsewhere in `run`. With functions aligned to 64 bytes (`-C llvm-args=-align-all-functions=6`) the difference is 0.2 ns at width 0 and about 2 percent at width 64 on `add-int`/`do-int`; with blocks aligned to 16 bytes, width 64 is level and width 0 differs by about 0.15 ns. It is codegen of the interpreter loop, not executed work; moving the arm's body out of line did not change it. Left to the maintainer: pin code alignment in the build profile, or look for a form of the slot release that adds no arm to `run`.
