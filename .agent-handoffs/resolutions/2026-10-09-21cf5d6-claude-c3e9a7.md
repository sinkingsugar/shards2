## 2026-10-09-c962880-claude-bdb2b4#F1
- Disposition: fixed
- Change/reason: `crates/shards-lang/src/lower.rs` (`read_name`, `const_expansion_limit`): every read of a constant adds its value's source length to a per-program total; past `EvalLimits::default().value_bytes` (1 MiB natively, 4 KiB on ESP-IDF) the read is `expansion-budget` (kept outside `problems`, which a repeated read truncates) and every later read stops at once. The per-read lowering stays, so diagnostics inside a constant keep the reading occurrence. Documented in docs/metaprogramming.md §2.5 (Constants). The limit reuses the platform default value limit rather than a separate constant; challenge it if a separate one is preferred.
- Evidence: `probe_const_growth` (release): 4 levels 37 ms (loads), 5 to 7 levels about 140 ms each, ending in `expansion-budget`; before, 7 levels took 22 s. New test `constants_built_from_each_other_stop_at_the_expansion_budget` (`lang.rs`, 0.45 s in debug; runs on the device in CI).

## 2026-10-09-b28886e-claude-584e8f#F1
- Disposition: fixed
- Change/reason: (1) `compose_time::Walk`: `text_size` and `Meter::nest` walk a value with one open iterator per level instead of queueing every waiting element, so their memory follows the nesting (at most 64 levels in an evaluation), not the element count; a table's keys are measured with the cap check per key. (2) The ESP-IDF default fuel is 8,000 instead of 20,000, so an evaluation allocates at most about 8 KB. (3) New test `an_evaluation_retaining_what_it_allocates_ends_at_its_budget` keeps every sequence it allocates until the budget ends it, under the platform defaults. (4) The firmware logs the heap low-water before each test (`examples/esp32/build.rs`), so a drop is attributed to the test between two lines.
- Evidence: unit test `walks_hold_one_iterator_per_level` (three levels of 1,000 elements, at most 3 open iterators, fuel equal to the node count). On the device (run above) the allocation test and every M8 test leave the low-water unchanged; the classic ESP32's low-water of 11,340 B (C3 42,816, S3 106,288) is set by `deep_do_chains_are_a_diagnostic_not_a_crash`, a compose-depth test that runs no evaluation, as on `main` (14,944 B there; the 3.6 KB difference is in that test, plausibly the larger per-level compose state, not isolated). An evaluation's 8 KB therefore fits below the measured minimum of the run, but not at that test's peak; the limit remains a host setting (`Mesh::set_eval_limits`).
