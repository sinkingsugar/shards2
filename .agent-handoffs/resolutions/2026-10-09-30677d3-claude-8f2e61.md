## 2026-10-09-21cf5d6-claude-4d1cda#F1
- Disposition: fixed
- Change/reason: `crates/shards-lang/src/lower.rs`. A constant without a `#( )` is lowered once (`read_value_const`) to a value every read shares (`const_values`); built from other constants, its size as text must be within `EvalLimits::default().value_bytes` (1 MiB natively, 4 KiB on ESP-IDF), measured with `text_size`'s early exit, `expansion-budget` at its definition. Reads cost nothing per read, so the number of reads no longer matters. A constant holding a `#( )` is still lowered at each read (its pipelines stay recorded under the reading occurrence); those reads are bounded by the source-map nodes they add, `EVAL_CONST_NODES` = 32,768 natively and 128 on ESP-IDF, each read charging the nodes it added itself so a runaway chain stops within one constant's own lowering of the bound. Documented in docs/metaprogramming.md §2.5 (Constants).
- Correction on the way: 4e58787 bounded `#( )` constant reads by source bytes, which does not bound memory: each re-lowering adds a source-map node per step (about 140 B on 64-bit), so the 4 KiB device budget took a 49,152-byte allocation (the source map's `Vec<SourceNode>`) and aborted on the C3 and the classic ESP32, and the 1 MiB native budget crashed Node in the wasm job ([ESP32 run 37913349065](https://github.com/sinkingsugar/shards2/actions/runs/37913349065), [CI run 37913349012](https://github.com/sinkingsugar/shards2/actions/runs/37913349012), both failed). c41edb8 counts nodes instead. c41edb8's device run then failed in the new lookup-table test, sized at 50 reads on the device: every top-level statement costs a few KB of compose state there, which ran the classic chip out of heap ([run 37914483066](https://github.com/sinkingsugar/shards2/actions/runs/37914483066)); 30677d3 uses 16 reads of a 100-element table on the device (about 6.4 KB of reads, past the old 4 KiB per-read bound).
