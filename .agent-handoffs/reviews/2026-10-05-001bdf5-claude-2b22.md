## F1 — P2 The compose depth limit does not protect the debug stackful scheduler
- Location: crates/shards-core/src/compose.rs (`MAX_FLOW_DEPTH` = 48), together with the stackful scheduler's 128 KB coroutine stack (crates/shards-core/src/runtime/mesh.rs)
- Evidence: chains of k wires, where wire i is `<shard>` around `Do(w(i+1))`, end in `1 | Log`; the entry is `Do(w0)`. These pass `check` (they are under the limit) and then segfault with exit 139 and no message on the debug stackful scheduler:
  - `If(All({true} { Do(next) true }) {1})`, k=15 (about 45 flow levels);
  - `When({true} { Do(next) })`, k=22 (about 44);
  - `Repeat({ Do(next) } Times: 1)`, k=22 (about 44).

  At k = 8, 10, 12, 15, 18 and 22, release builds on both schedulers and debug stackless all exited 0 or 1. Plain `Do` chains of 40 run, and chains of 80, 400 or 3000 give `too-deep`, as the commit says.
- Impact: how much stack one level takes depends on the shard, so the limit does not stop stack overflow. `cargo test` runs debug, and the 001bdf5 regression test only uses plain `Do` chains, which take the least stack per level.
- Suggested direction: larger coroutine stacks in debug builds, or a lower limit, or both. Add a test at `MAX_FLOW_DEPTH` through each control-flow shard on the stackful scheduler.

## F2 — P3 Push `Clear` is described as 1.x behavior, but differs within an iteration
- Location: crates/shards-core/src/shards/data.rs (`PUSH_PARAMS` `Clear` help: "as in 1.x"); the 001bdf5 commit message
- Evidence: 1.x's declaring Push clears on every activation (`../shards/shards/modules/core/core.hpp:2319`, `if (_clear && _firstPush)`, with no iteration check). For `Repeat({1 >> s  s | Count | Log("in")} Times: 3)`:
  - 1.x Release logs `in: 1` three times;
  - 2.0 at 001bdf5 logs `in: 1`, `in: 2`, `in: 3`.

  For a looped wire with `Once({0 >> s})` and `s | Count`, then `1 >> t` and `2 >> t`, both runtimes log `count: 1` and `t: [1 2]` on each of three iterations.
- Impact: this is about documentation and porting. 2.0's behavior is arguably more useful, but the help text and the deviations list do not match the code.
- Suggested direction: keep 2.0's behavior; describe it without "as in 1.x" and add it to the deviations from 1.x in docs/current-state.md.
