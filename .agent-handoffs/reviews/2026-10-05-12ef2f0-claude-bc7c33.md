## Scratch lifetimes
- `lower_scratch_releases` is a forward pass that tracks whether `scratch` may own a value. It starts at true, and is set true again after `Fallback`, `SeqMake`, `TableMake`, `Take`, `Push`, and `AddFloat4Const`/`AddFloat4Bound`. Those are exactly the arms of `run` that assign `scratch`: the entry input, the Take/Push results and the generic Float4 fallback. Typed Int/Float/Float4 arms write only `numeric`, so leaving the flag unchanged after them is sound. They also require numeric input, so any value left in `scratch` owns nothing. The first Const/Get/Set/Inc while the flag is set becomes its `*Drop` variant. Each `*Drop` arm reanchors `value` before assigning `scratch = Var::None`, and SetDrop clones from `value` before clearing, so no pointer outlives its owner. The match is exhaustive, so a new opcode cannot silently skip this classification.
- Entry invariant: the analysis assumes `run` is entered only at a segment boundary. I checked that this holds. `compose_flow_at_depth` is the only place a `CompiledFlow` is created, and it lowers the code there. Both flow loops call `run` only at index 0, after a fallback node, or at the index `construct` returns (after a constructor). Stackless `FlowState.resume` is assigned only at `stackless/mod.rs:319`, with the index of a node that returned `Suspend`, which is always a fallback. `run` does not itself assert this precondition; a `debug_assert` would be cheap hardening, but nothing violates it today.
- Behavior: every retention repro from the earlier reviews (`[acc] | Count`, `{a: acc} | Count`, `[acc]` or `{a: acc}` followed directly by `1 | Push`, via Take, via Get, after Set, consecutive constructors, and the `| Count` control) completes 40,000 iterations in 9–17 ms on both schedulers at 12ef2f0, printing `40000`. These are single wall-clock runs. The new unit test `owned_input_is_released_after_a_generic_boundary` and the prototype change (a `Const(None)` prefix, so the constructor is entered after a segment that does not own its input) cover the boundary re-arm case that a stale flag would break.

## Get offset safety
- `SlotOffset` has a private field and is constructed only through `SlotOffset::new`, which uses `checked_mul(size_of::<Var>())`. So every offset is a whole-`Var` multiple, and alignment follows from the base pointer's alignment. The frame byte length is `size_of_val(frame)`, which equals `len * size_of::<Var>()`. Since both values are multiples of the `Var` size, `offset < bytes` implies `offset + size_of::<Var>() <= bytes`. An empty frame (length 0) rejects every offset. The pointer comes from `base.cast::<u8>().add(offset).cast::<Var>()` on the raw base derived once from the exclusive borrow, so provenance stays inside the frame allocation and no intermediate reference is created. Separate `GetLocal` and `GetMesh` opcodes, each checked against its own frame's byte length, prevent a longer other frame from validating a bad offset; `specialized_get_checks_the_selected_frame` covers that case, plus multiplication overflow. The `assert!` stays in release builds. Set, Inc and Push still use index-based `slot` with `assert!(index < len)`. Shared compiled data holds no instance pointer.
- `#[repr(u8)]` on a data-carrying enum is a valid primitive representation. No unsafe code relies on the tag layout. The 32-byte instruction stride is a measured property (`layout-metadata.json`), not a correctness dependency.

## Benchmark evidence
- Provenance: `sha256sum -c` of `explicit-opcodes/runtime-source.sha256` passes against the 12ef2f0 checkout. `compose-cleanup/runtime-source.sha256` passes against `git archive 4b52472`. Both result sets therefore correspond to the committed sources they claim.
- The full-suite tables reproduce from `summary.csv` (width-256 medians). Const(Int) 127.8 against 125.3, Get(Int) 145.9 against 128.7, and the Add, Assign and Take rows match the doc. Recomputed from `summary.csv`, both results meet ≤2× in 21 of 25 cases. In the explicit-opcodes run the remaining four are make-seq 3.15×, make-table 3.08×, push-shared-seq 3.35× and take-table 3.59×, matching the stated range of 3.08–3.59×.
- The four-way matrix (`layout-matrix.json`, 486 records) reproduces the doc's width-256 stackless table exactly when the median is taken over the retained batches (warmups dropped), for example Const(Int) 180.3, 141.6, 173.3 and 127.3. It supports the conclusion: at width 256, explicit tags alone give 0.78–0.83× on Const/Get and offsets alone give about 0.76× on Get only, and the two combine to about 0.57–0.71× on Const/Get, on both schedulers. The 1.x binary is one hash-identified build in every cell, and the driver checks every output and count through the shared validator.
- Limits the docs mostly state but that are worth keeping in view:
  - Frequency is unlocked. The order rotates, but the paired cells are not simultaneous.
  - Width 8 shows smaller effects and some regressions that the width-256 tables do not show: tag-and-offsets Take(Seq) 1.05× stackless and 1.00× stackful against the baseline; offsets-only Assign(Int) 1.10× and 1.05×, and Add(Float) 1.045× stackless. The docs point to the retained data for short widths rather than tabulating these.
  - The matrix binaries were built before a test/comment addition. Their hashes differ from the final binary, but `layout-metadata.json` records the same `inline::run` size and address.
  - The 1.x wrapping-Add description is a static reading of one disassembly excerpt (`asm-1x.txt`, `vpaddq`). It is consistent with the cited excerpt; I did not check the 1.x source.
