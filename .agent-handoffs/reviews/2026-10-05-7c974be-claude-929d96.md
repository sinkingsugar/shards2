## F1 — P2 Seq.Make/Table.Make state retains the last output, making later in-place updates of captured values O(n)
- Location: `crates/shards-core/src/shards/data.rs:424` (`SeqMake::activate`) and `:537` (`TableMake::activate`); state introduced in `instantiate` of both.
- Evidence: instance state now keeps an `Arc` of the last constructed collection, so every element it captured keeps an extra reference until that constructor runs again or the instance is cleaned up. A captured sequence variable is therefore never unique when a later `Push` reaches `Arc::make_mut`, and each push copies the whole sequence. Script (stackless default; `--stackful` identical):

  ```
  [] >= acc
  Repeat({
    [acc] | Count
    1 | Push(acc Clear: false)
  } Times: 40000)
  acc | Count
  ```

  `shards2 run`: 98a75c6 8 ms, 7c974be 2457 ms (stackful 8 ms vs 2482 ms). Same with `{a: acc} | Count`: 14 ms vs 2434 ms (stackful 12 vs 2468). Control without the constructor (`1 | Push(acc Clear: false)` only): 4 ms vs 3 ms. All runs output `40000`, so the results are unchanged; only cost changes.
- Impact: this pattern (build a temporary collection that mentions an accumulator, then keep growing the accumulator) was linear before and is now quadratic on both schedulers. Separately, the state keeps captured values (large strings, sequences, tables) alive beyond their last use, indefinitely for a constructor that does not run again (inside `Once`, an untaken branch, or a finished loop). The documented contract ("reuse it only when no saved output shares it") holds for the output buffer, but the docs and the new tests do not cover this side effect on captured elements. The regression tests check only output-snapshot correctness, which is why the suite passes.
- Suggested direction: do not hold element references between activations. For example, reclaim only an allocation that the consumer has already dropped and emptied, or revert the reuse: the follow-up table still reports make-seq at 8.26× and make-table at 5.67× slower than 1.x, so the reuse does not appear to pay for this trade-off. Add a shared-suite regression that asserts linear behavior or uniqueness: for example, check `Arc::strong_count` through a test shard, or use a work-count bound rather than wall time.

## Notes (not findings)

- Inline executor soundness: I found no defect in the pointer accumulator. Reads finish before each write in every arm. `Set` skips self-copies by pointer identity. `Push` snapshots into `scratch` before mutating a possibly aliased slot. `Take` and `Push` reuse `scratch` only after the read. `numeric` is written only with `Int`/`Float`/`Float4`, so skipping its drop leaks nothing, and the error paths drop `scratch` normally. `Set`/`Ref`/`Update` have identical generic activations, so mapping all three to `Op::Set` preserves behavior. For Float4 + Float4, adding in `f32` matches the generic path (add in f64, round to f32), because f64 has at least 2·24+2 bits and double rounding is exact for addition. Mixed shapes use `math::arith`. One difference: a runtime operand mismatch reports `inline builtin: operand type mismatch` instead of `Math.Add: ...`. Compose types and the asserting `set_var` make this unreachable, as far as I found.
- Stackful segments take `ctx.mesh.borrow_mut()` for every inline segment, including segments that touch only locals. No shard was found that holds a mesh borrow across a nested flow activation, but this is a new reentrancy assumption. A segment that does not touch mesh bindings could skip the borrow.
- Pre-existing behavior, outside this diff: `acc | ExpectSeq | Count` (or `| Log |`) followed by `Push(acc Clear: false)` is already quadratic at 98a75c6 (about 1.7 to 2.1 s for 20,000 iterations at both commits, against 8 ms for `acc | Count`). Something retains a passthrough output across the next shard. This was not root-caused; it is noted so that F1's fix is not mistaken for this cause, and it may deserve its own investigation.
- The benchmark raw data, slopes and the 1.x side were not re-audited in this record.
