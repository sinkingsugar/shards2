## F1 — P2 The frontend, not the engine, dominates the heap the device suite needs
- Location: `crates/shards-lang/src/lexer.rs` (`Token`, 72 bytes), `crates/shards-lang/src/ast.rs` (`Block`, 104 bytes), `crates/shards-lang/src/parser.rs`, `crates/shards-lang/src/lower.rs` (`SourceMap`).
- Evidence, `do_chain(80)` (1,682 bytes of source, the fixture `deep_do_chains_are_a_diagnostic_not_a_crash` checks, and the test the ESP32 run dies in): `parse` alone peaks at 195,204 bytes and its result retains 120,328; `Program::load` peaks at 197,915; `check` peaks at 243,932. That is about 116 times the source size for parsing, or 2.4 KB per one-line wire.
- Evidence, the full-depth `When` chain (23 wires): `load` peaks at 108,192 bytes, `load` + `compose` at 181,214, with `run` 198,580, and `load` + `analyze` 493,503. The engine's share (instantiate and run) is about 17 KB. At c0aaa39 the same fixture peaked at 5,354,121 bytes in compose, so the M4 follow-up commits cut compose about 27 times; before M4 this fixture could not have run on a device at all.
- Evidence, retention: repeating the same parse, compose and run retains about 20 bytes a round, and a new table shape about 150 bytes, so memory is not accumulating across tests. The failures are per-fixture peaks.
- Impact: this answers the open question in `2026-10-06-ab4bc6b-codex-ace9ae#F1` (new runtime regression or untested frontend cost): it is frontend and compose cost that no device run exercised before M4. Work on engine state will not close the gate.
- Suggested direction: free the token vector before lowering starts and shrink `Token` and the AST nodes (names as spans into the source instead of owned `String`s); avoid keeping tokens, AST, lowered definitions and source map alive together. The compose share is next (73 KB at full depth, growing faster than linearly: 25 KB at 11 wires, 41 KB at 17). Rerun these two fixtures under a counting allocator as the measure of progress.

## F2 — P3 The tooling report at full nesting depth lost its native test
- Location: `crates/shards-lang/tests/lang.rs`, `nesting_up_to_the_limit_runs_through_every_control_shard` and the 30-level `When` test.
- Evidence: both replaced `check(&src).ok()` with `Program::compose`, on every target, to spare the device the occurrence report. `check` on a chain one wire too deep is still tested, but that path stops at `too-deep`. No test now runs `analyze` on the deepest program that composes. Run by hand, `shards2 check --json` on the 23-wire `When` chain returns `ok: true` with a 101,948-byte report in debug and release, so nothing is broken today.
- Impact: a stack overflow or quadratic blow-up in the report at the limit would pass CI.
- Suggested direction: keep `check(&src).ok()` under `cfg(not(target_os = "espidf"))` next to the device-sized assertion.
