## F1 — P2 Terminate subprocess descendants before joining their pipes on timeout
- Location: `bench/authoring/src/main.rs:150-161`, `run_with_timeout`.
- Evidence: the timeout kills only the immediate child, then unconditionally joins threads reading stdout/stderr and writing stdin. Model commands are run through `sh -c`, so descendants can retain those pipe handles after the shell is killed. In a temporary copy of the unchanged runner, calling the helper as below returned `timed_out=true` only after **2004 ms**, despite the **100 ms** timeout:

  ```rust
  let mut cmd = Command::new("sh");
  cmd.args(["-c", "sleep 2 & wait"]);
  let start = Instant::now();
  let out = run_with_timeout(cmd, "", Duration::from_millis(100)).unwrap();
  println!("{} {:?}", out.timed_out, start.elapsed());
  ```

  This was compiled from a copy of the reviewed `main.rs`, replacing only its entry point with the repro; no timeout implementation change was made. The finite sleep allows the repro to clean itself up. An indefinitely running descendant instead leaves the join blocked indefinitely. Descendants retaining pipes can also block these joins when the immediate child exits normally.
- Impact: the advertised model timeout does not bound task execution; a stalled model CLI or wrapper can hang a worker and prevent the evaluation from completing, while its subprocess continues running.
- Suggested direction: own and terminate the subprocess tree/process group and ensure pipe readers/writer cannot outlive the deadline indefinitely. Add a regression with a shell spawning a pipe-inheriting child, including the case where the shell exits first.

## F2 — P2 Parse schedule declarations instead of splitting their source on whitespace
- Location: `bench/authoring/src/main.rs:224-228`, `outcome_names`.
- Evidence: the following valid program passed the current CLI's `check --json` and ran successfully:

  ```shards
  @wire(main { 1 | Log }) @mesh(m) @schedule(m,main) @run(m)
  ```

  Actual stdout was `1\nmain: 1\n`. Calling the runner's unchanged `outcome_names` on this source returned only `["root"]`; `log_matches` with expected `["1"]` returned false. The language allows commas, but `split_whitespace().nth(1)` cannot find the wire in `m,main`. Consequently a correct model answer is scored `wrong-output` solely because of valid formatting. This also affects a comma directly after the wire name, such as `@schedule(m main,)`.
- Impact: semantic success scores for scheduler tasks depend on superficial syntax choices, undermining comparisons between models/variants. The saved baseline uses the supported spelling, so this finding does not change its recorded results.
- Suggested direction: obtain outcomes/logs through structured CLI output or the real language parser; avoid reimplementing syntax with substring matching. Add equivalent comma-separated and whitespace-separated schedule cases.
