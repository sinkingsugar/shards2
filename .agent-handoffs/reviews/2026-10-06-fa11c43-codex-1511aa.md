## F1 — P2 Reject computed expressions as declaration targets
- Location: `crates/shards-core/src/shards/mod.rs:330-332` (`check_declaration`), reached through `crates/shards-lang/src/lower.rs:1070` (computed argument hoisting).
- Evidence: these programs all check and run successfully on both schedulers:

  ```shards
  1 | Var((2))
  ```

  ```shards
  Keep((0) 10)
  ```

  ```shards
  {count: 1} = obj
  7 | Var(obj.count)
  obj.count | Log
  ```

  The last program logs `1`, while reporting success. A declaration requires a name; these supplied an expression or a path. Lowering treats any parameter accepting `Forms::VARIABLE` as eligible for computed-value hoisting, evaluates the target expression into an immutable `%n` binding, and passes that generated name as the declaration target. The new shared declaration checker exempts `%` names, so Var/Keep silently allocate another inaccessible slot instead of rejecting the malformed declaration.
- Impact: invalid declaration targets silently succeed, with discarded state and misleading behavior. The new language's explicit declaration contract is not enforced at the frontend boundary; a typo involving a field path can appear to work while leaving the intended value unchanged.
- Suggested direction: distinguish variable-name targets from readable operand values when lowering. Require a plain identifier for Var/Keep (and other variable-target parameters), rather than hoisting an expression into a declaration name. Preserve temporary bindings for real computed operands. Add shared frontend regressions for parenthesized literals and field paths as targets.
