## F1 — P1 Include state destroyed by an inline-triggered wire swap in reset admission
- Location: `crates/shards-core/src/stackless/runtime.rs:321` (`validate_reload`), `:394` (`install_revision`), `:718` (`swap_body`).
- Evidence: a looped wire calls an unchanged stateful Counter with `Keep(n 0)`, logs it, then calls a small stateless ReviewAdd. Run two ticks, edit only ReviewAdd's arithmetic, and preserve-reload under the default `ResetPolicy::Reject`. Reload succeeds, but the next logged counter is 1 rather than 3: `["1", "2", "1"]`. Under `Apply`, the report is `ReloadReport { retained: [], reset: [], restarted: [], swapped: ["main"] }` even though Counter's persistent state was destroyed. Both `review_inline_reload_does_not_silently_reset_unchanged_component` and `review_inline_reload_reports_component_reset_under_apply` fail in debug/release at the reviewed SHA and pass on d30f56a.
- Cause: validation skips unchanged function bodies at `same_body`, so it records no reset for Counter. Inlining adds a swap dependency for ReviewAdd, and `swap_body` cleans the entire engine, preserving only the wire's own Keep locals. Component Keep slots, native state and continuations are discarded regardless of whether their own definitions changed.
- Impact: an edit to an unrelated arithmetic helper silently loses application state despite the host's explicit reject-resets policy. The swapped-wire label does not identify or authorize the lost component state. This remains a defect even accepting the documented decision to swap a caller after an inlined dependency changes.
- Suggested direction: model the actual state transition during validation, including everything a wire swap destroys. Prefer preserving unaffected components; if reset is necessary, reject it under Reject and enumerate the affected state under Apply before installation.

## F2 — P2 Release completed invocation values before the caller mutates their collections
- Location: `crates/shards-core/src/compose.rs:655–683` (hidden inlined slots), `crates/shards-core/src/stackless/engine.rs:679` (cached invocation reset); the VM call path similarly retains locals in `inline.rs::vm_call_op`.
- Evidence: put a uniquely owned `[7]` sequence in mesh variable `acc`; call `Read(input: [Int] output: Int { input | Take(0) })`, discard the scalar result, then `1 | Push(acc)` and pause. The sequence has the correct contents `[7, 1]`, but its Arc allocation changes: the completed Read still owns the old sequence in its hidden input slot. Adding Log to Read forces the framed path and exhibits the same copy. `review_completed_inlined_call_releases_input` and `review_completed_framed_call_releases_input` independently fail their allocation-identity assertions in native debug/release. Both source fixtures pass on d30f56a, where invocations release their frames on completion (the “inlined” fixture takes the older frame path there).
- Cause: inlining writes the call input/arguments to hidden caller slots but emits no lifetime-end operation; cached frame completion also leaves invocation locals populated. Entry-time clearing is too late for caller-side mutations between calls. Definite assignment prevents stale reads but does not release obsolete Arc owners.
- Impact: repeating read-then-push on a growing sequence copies its entire buffer on every iteration, making otherwise unique append work quadratic. Dead argument/local collections can also remain retained across caller suspension until the next entry or enclosing-frame reset.
- Suggested direction: end invocation value lifetimes on success and failure, preserving any returned output as an owned snapshot first. Clear the inlined slot range and cached invocation locals when the call exits; account for exceptions before a normal inlined epilogue. Keep frame allocation reuse separate from value ownership.
- Relation to earlier findings: this is a new owner introduced by retained/inlined calls, not a reopening of [2026-10-05-a003cb7-claude-3dc841#F1](2026-10-05-a003cb7-claude-3dc841.md)'s fixed VM-input-scratch owner. The exact collection-copy symptom has recurred through a different path.

## F3 — P2 Roll back initialized siblings when cached stateless re-entry fails
- Location: `crates/shards-core/src/stackless/engine.rs:702–715` (`revive_invocation`), and the `Request::Prepare` error arm around `:930`.
- Evidence: a stateless Work contains a resource-counting Probe followed by a host shard that succeeds on its first instantiate and fails on its second. Invoke Work through Maybe in a looped wire. Tick 1 succeeds and cleans the first invocation; tick 2 reinstantiates the Probe, then catches the later instantiate error. Outputs are correctly `["1", "-1"]`, but the Probe has two successful instantiations and only one cleanup after tick 2. `review_failed_stateless_reentry_rolls_back_initialized_siblings` fails in debug/release with cleanup count 1 versus expected 2. It passes on d30f56a.
- Cause: `revive_invocation` writes each initialized state into the cached tree and propagates the first error with `?`. The prepare-error arm resets only the continuation, bypassing the stateless-call completion/reset path. Earlier initialized siblings remain live; a subsequent attempt skips them because they are no longer Pending.
- Impact: resources from an invocation that failed to initialize survive a caught failure and may be reused by a later invocation. This violates per-invocation initialization/cleanup semantics and can retain resources indefinitely while the caller continues or waits. They remain arena-owned and can be cleaned at eventual owner teardown; this is not an unreachable-frame leak.
- Suggested direction: make cached re-entry transactional using the same rollback discipline as initial build. On error, clean every state initialized for that attempt and restore Pending markers before returning to Maybe. Preserve cleanup-panic handling and retryability.
- Relation to earlier findings: distinct from [2026-10-06-d30f56a-astra-6c92e1#F2](2026-10-06-d30f56a-astra-6c92e1.md), whose fixed defect detached an old stateful component during migration. That verified fix remains closed.
