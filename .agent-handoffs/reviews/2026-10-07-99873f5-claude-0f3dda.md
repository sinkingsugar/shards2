## F1 — P2 Editing a framed callee swaps every wire that spawns a wire calling it
- Location: `crates/shards-core/src/reload.rs:131` (`retention`: `Dep::Inlined { .. } | Dep::Function { .. } => Retention::Swap`) and `crates/shards-core/src/compose.rs:1013` (`compose_wire` copies the spawned wire's `deps`, `Dep::Function` included, into the spawner's `restart_deps`).
- Evidence: `compose_call` records a framed callee as `Dep::Function` in `deps` only, by design (`function_def`, "a callee's edit never restarts its callers"), and `same_body` ignores it. But `compose_wire` copies the child's whole `deps` list into the spawner's `restart_deps`, and `retention` now maps a stale `Dep::Function` there to `Swap`. Repro (preserving reload through `Session`, first `F` returning 1, then 10):
  ```
  @fn(F input: None output: Int params: {} { Pause() 1 })
  @wire(child { F | Log("child") })
  @wire(main { Spawn(child) Log("a") Pause() Log("b") })
  @mesh(m) @schedule(m main) @run(m)
  ```
  After one tick (`a` logged, `main` paused) the edit of `F` is accepted with `swapped == ["main"]`; the following ticks log `a` again, then `b`: `main`'s iteration was cut and rerun. Expected under §11 and under the range's own description (`current-state.md:40`: callees that keep their frames follow §11 unchanged; `reload.rs:96`: `swapped` lists wires "because a function inlined into it changed"): `main` reused untouched, `a` once, `b` once; `child`'s call site selects the new `F` at its next entry. `F` is not inlined anywhere here (its body suspends), and `child`'s compiled body is the same program, so the spawner's embedded `Arc<CompiledWire>` needs no replacement. Before this range the same dependency made `reusable` false and restarted `main`, so this is an over-reaction the range recategorised rather than introduced.
- Impact: in `shards2 watch`, every save of a function called from any spawned wire cuts the spawner's iteration in flight and replays its side effects (here a second `Spawn`, which is also why two `child: 10` lines appear). It contradicts the contract that framed callees are selected at entry and never disturb their callers, and the report attributes the swap to inlining.
- Suggested direction: make `retention` consistent with `same_body` (a stale `Dep::Function` is `Reuse`), or stop `compose_wire` from copying `Dep::Function` into `restart_deps` (the spawner embeds the child's compiled body, so `Dep::Inlined`, `Dep::Wire` and `Dep::MeshVar` must still propagate). Add the repro as a regression test asserting an empty report and `a, b` once.

## F2 — P2 A swap ends the iteration in flight instead of letting it finish on its pinned body
- Location: `crates/shards-core/src/stackless/runtime.rs:379-396` (the swap loop in `install_revision`) and `:718` (`swap_body`: cleans up the instance's state, lays out fresh locals, `started = false`).
- Evidence: repro with a wire that is not looped and is suspended mid-iteration when its inlined callee is edited (`Step` adds 1, then 10):
  ```
  @fn(Step input: Int output: Int params: {} { Math.Add(1) })
  @wire(main { Log("a") Pause() 1 | Step | Log("b") })
  @mesh(m) @schedule(m main) @run(m)
  ```
  One tick logs `a`; the edit is accepted with `swapped == ["main"]`, `restarted == []`; the next ticks log `a` again and then `b: 11`. The wire's single run was restarted from the top on the new body, yet it is reported as swapped, not restarted. For a looped wire the same cut applies to the iteration in flight. §11 says "An in-flight invocation finishes on its pinned body" and "Retention or reset happens only at an inactive component boundary"; the deviation paragraph in `current-state.md:40` describes the cut ("cleaning up the iteration in flight") but `docs/golden-path.md` §11, which AGENTS.md names as the contract that overrides other documents, still states the opposite, and nothing says what a non-looped wire does.
- Impact: side effects already performed in the cut iteration are redone (logs, spawns, pushes to mesh sequences, HTTP requests), on every save of a small helper in `watch`. The engine already has the boundary at which a looped wire resets its non-persistent locals (`runtime.rs` `step`, the `Step::Next | Step::Return | Step::Restart` arm), so finishing the iteration costs nothing architecturally. This is a design decision for the author; the finding is that the implemented policy, the contract and the report disagree.
- Suggested direction: either defer the swap to the iteration boundary (keep the candidate body pending on the `Instance`, apply it where `step` resets the locals; a non-looped wire then completes on its old body, which is what §11 says), or, if the immediate cut is the chosen policy, amend §11 and report a non-looped wire whose run is restarted under `restarted`. Either way add a test for the non-looped case and one asserting a looped wire's in-flight iteration completes (or is cut) as decided.

## F3 — P3 The reload contract was not updated for inlined sites
- Location: `docs/golden-path.md:259-262` (§11); the deviation is recorded only at `docs/current-state.md:40` and in doc comments.
- Evidence: §11 reads as if every call site selects at entry and in-flight invocations always finish on their pinned body; after this range an inlined site is part of its caller's body and takes effect at the caller's next entry, and a wire body is swapped. AGENTS.md says golden-path.md "overrides older statements in the documents below where they conflict", so a reader of the contract alone is now misled.
- Impact: documentation only; the next person designing against §11 (for example the `Match`/`Once`/`Maybe` flattening stages listed as next) would design against the wrong rule.
- Suggested direction: one sentence in §11 pointing to the inlined-site rule and the swap (as finally decided under F2), keeping the detailed deviation in `current-state.md`.

## Checked and found no problem

Listed so the implementer need not re-derive them; each is this session's own inspection or repro, not a certification of the whole runtime.

- `Instruction::for_each_local` covers every op that addresses a local (checked against the `Op` enum: the ops left alone are constants, mesh reads, `TakeSlot` whose operand indexes a table slot, jumps, `VmCall` and `Fallback`); `rebase_locals` runs before `relocate`, so slot and jump offsets are independent.
- `vm_leaf` excludes `VmCall` and `Fallback`, so a body with a call site or a shard activation is never inlined; `scratch_slots` is a subset of `locals`, so the uncleared hidden slots can only leak a value into a read that precedes every write, which compose rejects (`unknown-variable` for a read after a conditional `Var` inside `When`), and `Push`/`Inc` on a `None` slot fail rather than accumulate.
- Input read by name plus arguments at two sites inside a `Repeat` computes correctly (`@fn(G input: Int output: Int params: {k: Int} { k | Math.Add(input) })`, `0 | Var(acc) Repeat({ acc | G(k: 3) | G(k: 4) | Update(acc) } times: 3) acc` gives 21).
- A two-level chain (`main` inlines `F` inlines `G`) recomposes and swaps when `G` is edited (`2` then `24`), so `Dep::Inlined` reaches both the compose cache and `restart_deps` transitively.
- A stateful function that inlines an edited callee keeps its `Keep` (`retained == ["Counter.n"]`, output `2, 3, 13`), so `same_body` counting `Dep::Inlined` composes with the §11 state rules.
- An incompatible edit of an inlined callee (`G` now outputs `String`) is reported as a compose error at the embedding function's `Math.Multiply` with the input source `0:G` named, at line 2 of the candidate.
- A VM error raised at a `VmCall` instruction (second call onward) under `Maybe` in a looped wire behaves identically on four iterations; skipping the `Control` branch on `vm_error` does not leave a stale continuation, and the `Complete` path never indexes `states[node]`.
- Runtime errors carry no source location on either the inlined or the framed path (`activation error: Math.Divide: division by zero` for both); inlining does not degrade diagnostics, and the lack of location predates this range.
