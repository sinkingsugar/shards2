## F1 — P3 The expansion bound counts every read, so ordinary lookup-table constants are refused, much earlier on the device
- Location: `crates/shards-lang/src/lower.rs` `read_name` (the `const_expansion` counter) and `const_expansion_limit`
- Evidence: a 5,000-element lookup table (`@const(lut [...])`, 19,451 bytes of source) read with `@lut | Take(i)` loads at 10 and 40 reads and fails at 80 reads with `expansion-budget`. Nothing nests: the cost comes only from re-lowering at each read. On ESP-IDF the total is 4 KiB, so for example a 100-byte constant read in 41 places fails to load on the device but loads natively. The re-lowering does duplicate real memory today (80 copies of the table), so the bound is not baseless. But what it measures is an artifact of "lowered at each read", not something the program asks for. "Lookup tables" is the use §1 names first.
- Impact: hard-to-predict load failures on valid programs that grow with the number of reads, and the same script behaves differently on native and device for that reason alone.
- Suggested direction: lower each constant once to a value (a shared `Arc` `Var`, or one `Eval` flow) and reuse it at reads. Keep the source path only for locating diagnostics, which `read_const` already reports once. Then bound only what nesting creates (the output limit on the value), not the number of reads. Not blocking for the M8 gate if the author accepts the current limit and documents it in the primer.
