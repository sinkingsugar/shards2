## F1 — P2 Reads of a shared constant are free while lowering, but compose rebuilds a table constant in full at every read
- Location: `crates/shards-core/src/compose.rs` (argument decode: `Operand::Const(v.clone().into_struct_tables())` and the literal conversion in `args.rs`), `crates/shards-core/src/var.rs:178` `Var::into_struct_tables` (it rebuilds every sequence that holds a map table, element by element, so a shared value becomes a full tree); `crates/shards-lang/src/lower.rs` `read_value_const` now hands the same shared value to every read.
- Evidence: `@const(t0 {a: 1})`, then `@const(tN [@tN-1 ×8])` up to `t5` (about 852 KB as text, within the 1 MiB value limit), then `@t5 | Count | Log` repeated. `Program::load` then `compose()`:

  | Case | Load | Load + compose | Peak memory |
  |---|---|---|---|
  | 10 reads | 0.6 ms | 112 ms | 39 MB |
  | 100 reads (2,043-byte script) | 0.8 ms | 1.04 s | 356 MB |

  `check` behaves the same way. That is about 10 ms and 3.5 MB per read, growing linearly, so 1,000 reads (about 20 KB of source) would be about 3.5 GB. With sequences instead of tables (`T0="[1 2 3]"`, 4 levels, 100 reads) the peak stays at 4.6 MB, against 48 MB for tables at the same depth: the expansion comes from the table conversion. Before 4e58787, the per-read budget stopped this indirectly; removing it moved the amplification from lowering into compose.
- Impact: a short script again reaches hundreds of MB to GB without any budget applying (§2.2 "never a hang"). On the device the value limit is 4 KiB, so each read costs less, but whether the per-read copies stay resident in compiled code was not isolated.
- Suggested direction: convert a constant's tables to struct form once, when lowering shares it (or memoize `into_struct_tables` by `Arc` pointer so sharing survives), so decode's conversion is a no-op at each read. Add a regression test that composes many reads of a nested table constant and asserts bounded memory or time.
