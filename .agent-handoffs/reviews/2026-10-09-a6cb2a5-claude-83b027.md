## F1 — P2 The device acceptance suite aborts: the new table constant test exceeds the device's value limit
- Location: `crates/shards-lang/tests/lang.rs:2674` (`a_table_constant_built_from_copies_composes_as_it_is_held`, `(3, 16)` on ESP-IDF)
- Evidence: ESP32 [run 37924973862](https://github.com/sinkingsugar/shards2/actions/runs/37924973862) fails on esp32, esp32c3 and esp32s3 with `load failed: ... "expansion-budget", "`@t3` expands past 4096 bytes as text ..."` at t.shs:4:11, then `abort()`. The resolution says 3 levels fit "within its 4 KiB value limit", but `t3` is 8³ = 512 tables of about 26 bytes as text, about 13.9 KB. Two levels (about 1.8 KB) fit. The resolution lists the QEMU boots as not run.
- Impact: CI is red on the device, and the abort skips every acceptance test after this one on all three chips, so the device coverage of later tests (and the claim that both new tests run there) is not established.
- Suggested direction: use 2 levels on ESP-IDF (`(2, 16)`), and confirm the device run passes before claiming device coverage.

## F2 — P3 Equality does not remember map-table pairs, so a preserving reload still walks nested map-table constants path by path
- Location: `crates/shards-core/src/var.rs` `SameValues::tables`. Two `TableRepr::Map` values that are not `Arc::ptr_eq` fall to the generic branch, which never calls `remember`. Only sequences and struct tables are remembered.
- Evidence: literal tables from lowering are map tables, and a preserving reload compares the old and new definitions, which are separately built copies. Constants `@const(tN {a: @tN-1 b: @tN-1})` at 14 levels (within the 1 MiB value limit; 15 is `expansion-budget`), read inside a looped wire, then `Session::reload` followed by `reload_preserving` of the same source:

  | Shape and reads | Preserving reload |
  |---|---|
  | `[@t @t]` sequences, 100 reads | 3.0 ms |
  | `{a: @t b: @t}` tables, 10 reads | 24 ms |
  | `{a: @t b: @t}` tables, 100 reads | 154 ms |
  | `{a: @t b: @t}` tables, 1,000 reads (about 30 KB of source) | 1.44 s |

  The cost grows linearly with reads, and each read walks up to the value limit's worth of nodes.
- Impact: it is bounded (the value limit caps each read), so seconds rather than a hang. But under `watch` every save pays it, and the resolution's claim that equality of separately built values costs "what they hold" holds only for sequences and struct tables.
- Suggested direction: in `SameValues::tables`, remember map-table pairs by their entries' storage (after the length check), as `seqs` does. Extend `values_built_from_one_shared_value_cost_what_they_hold` with a map-table chain compared against a separately built copy.
