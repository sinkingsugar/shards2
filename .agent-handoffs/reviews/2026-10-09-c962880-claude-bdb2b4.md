## F1 — P2 `@const` literals that read each other grow exponentially while lowering, outside every budget
- Location: `crates/shards-lang/src/lower.rs:1551` (`read_const`) and `:1655` (`constant`): a constant is lowered again at each read.
- Evidence: `@const(c0 [1 2 3 4 5 6 7 8])` followed by `@const(cN [@cN-1 ×8])` lines. `Program::load` (release): 4 levels 32 ms, 5 levels 192 ms, 6 levels 1.77 s, 7 levels (a 362-byte script) 22 s, growing ×8 per line (probe `probe_const_growth`). No `#( )` is involved, so no fuel, value or output limit applies; the frontend builds a 2M-element literal that nobody wrote. Expected: a constant's size is bounded like the rest of compose-time work (§2.2: "never a hang"; defaults small enough for the device, which lowers on device).
- Impact: a few lines hang `check`, `watch` and the device's frontend; the same doubling reaches compose and the cache key hash when the constants hold `#( )` (each read copies the evaluation flows).
- Suggested direction: lower each constant once to a value (or one shared `Eval`) and reuse it at reads, keeping the per-read path only for locating diagnostics; or bound a pure-literal constant by the output limit.

## F2 — P2 `Match` compares cases without charging fuel, so one evaluation runs for seconds within its budget
- Location: `crates/shards-core/src/shards/control.rs:217` (`MatchCompiled::find`, `values_equal` per case); listed as constant work in `crates/shards-core/src/compose_time.rs:299`.
- Evidence: `#( 0 | Var(k) Repeat({ <4000-element literal, last element differs> | Match([<4000-element literal> {1}] default: {0}) Inc(k) } times: N) k )` (probe `probe_match_amplification`): N = 100,000 takes 1.16 s, N = 1,000,000 takes 11.8 s and succeeds; only N = 3,000,000 runs out of fuel (13 s). The cost grows linearly with the case literal, so a larger literal multiplies it further. `Is`, `IsNot` and `IsAny` traverse (and charge) both sides; `Match` does not. The comment "bounded by the code" makes the work per dispatch proportional to the source size, which §2.1 rules out ("charge fuel in proportion to its work ... not once per dispatch").
- Impact: the fuel budget no longer bounds evaluation time. With the device's 20,000 fuel the same shape is tens of millions of element comparisons.
- Suggested direction: when metered, `meter.traverse` the input once per activation (or charge per case compared by the smaller side's size), like `Equality`.

## F3 — P3 A `not-compose-time` caused by mesh access names neither the shard nor the function
- Location: `crates/shards-core/src/compose/evaluate.rs:329`: the mesh-access branch passes no occurrence, so the path is empty and the message says "cannot run the pipeline at compose time: it reaches mesh variable gain".
- Evidence: by the code path; `an_evaluation_reaching_mesh_access_is_not_compose_time` asserts only `contains("mesh variable gain")`. `Owner::Eval` hides mesh variables, so this branch is only reached through a function that declares `uses`/`mutates`, which is the one fact the user needs and is not reported, nor is "(reached through ...)". §2.1 requires a located diagnostic "naming the offending shard or function"; §2.4 asks for location also when it happens indirectly.
- Impact: in a deep call graph the user cannot tell which function brings in the mesh access.
- Suggested direction: record mesh-access occurrences (or the first `Get`/`Update` of a mesh binding) in `Analysis` like the other reasons, and assert the function name and location in the test.

## F4 — P3 `Dep::Evaluation` never reaches `restart_deps`, so its arm in `retention` is dead and the handoff's "restarts on reload" claim does not hold as written
- Location: `crates/shards-core/src/compose/evaluate.rs:128` (`record_evaluation` pushes `Dep::Evaluation` only to `deps`); `crates/shards-core/src/reload.rs:138`.
- Evidence: by inspection. If a host lowers its limits with `Mesh::set_eval_limits` between reloads, the wire's `deps` fail validation and recompose (reporting `expansion-budget`), which is acceptable behavior, but not through the `Restart` arm the record and §2.5 describe.
- Impact: documentation and dead code only; a future change relying on that arm would silently not get it.
- Suggested direction: either push `Dep::Evaluation` into `restart_deps` too (and test a reload after `set_eval_limits`), or drop the arm and correct §2.5/the record.

## F5 — P3 No device-sized fixture covers `#( )` nesting, which adds an engine run per level
- Location: `crates/shards-lang/tests/lang.rs` `nesting_up_to_the_limit_runs_through_every_control_shard` (wrappers list).
- Evidence: each `#( )` level adds `evaluate` → `compose_and_run` → a fresh `ComposeCtx` and an `Engine::activate` to the compose recursion while counting as one flow level. Natively 14 levels compose in a debug test thread (probe `probe_eval_chain_depth`, `CHAIN=14`; 15 is `too-deep`), but nothing checks the ESP32's smaller task stack at `MAX_FLOW_DEPTH = 24`, and the release nesting step does not include it.
- Impact: a stack overflow on the device rather than `too-deep` would only show up in the field.
- Suggested direction: add a `#( F )` function chain at the limit to the nesting test (it already runs in QEMU and in the release step).
