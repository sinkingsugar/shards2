## 2026-10-05-2d16cae-codex-7c92#F4
- Result: verified
- Evidence: by inspection, `Mesh::take_finished` takes no keep list on either scheduler (`crates/shards-core/src/runtime/mesh.rs:273`, `crates/shards-core/src/stackless/runtime.rs:241`). It drains every finished record in one `retain_mut` pass with no inner search. The runner (`crates/shards-lang/src/program.rs:281-301`) checks entry membership in a `HashSet` and moves entry outcomes into its own `HashMap`. Finished entries therefore leave the mesh on the tick they finish and are not rescanned, so per-tick retirement is O(records) plus hashed lookups. The quadratic `keep.contains` case from [the Codex verification](2026-10-05-d395707-codex-8c9d.md) no longer exists.
  - Correctness of the move: InstanceIds come from a monotonically increasing `next_id` on both schedulers and are never reused, so a later spawned child cannot be mistaken for a retired entry. `take_finished` runs after every `tick` and before the loop can break, so an entry that finishes on the last tick is still collected. `Program::run` is the only caller of `take_finished`.
  - Tests: `take_finished_drains_finished_records_in_one_pass` (prototype.rs) and `entry_outcomes_survive_retirement_of_finished_records` (lang.rs) pass on both schedulers. The Codex 64-entry recipe, run with `target/debug/shards2 run` with and without `--stackful`, exits 0 on both and prints all 64 entry outcomes plus `live: still running after 3 ticks`.
- Limits: the complexity result is from inspection; no timing was measured. Neither test detects a return to quadratic cost (the lang test would also pass on the code at 40e67d5), so they guard behavior, not scaling. `Host::take_outcome` (`program.rs:28`) is no longer called by the runner.
