## What changed and where to look

Stage two of flat control flow, agreed with the author: a call to a stateless, non-recursive, straight-line body of at most 24 instructions with no call site of its own is inlined into the caller's code at compose. Suggested focus, in order of risk:

1. `crates/shards-core/src/compose.rs`, the `Control::Call` arm of `ComposeCtx::flatten` and `Flat::append_rebased`: the conditions (`CallTarget::Direct`, not stateful, `vm_leaf`, no `Keep`, no lazy refs, `INLINE_BUDGET`, `inline_depth` below `INLINE_DEPTH`), the hidden slots for the callee's frame, the input saved only when the body reads `input` by name or arguments clobber the accumulator, argument binding, the `Const(None)` prelude for an input-ignoring callee, and `Instruction::rebase_locals`/`for_each_local` in `inline.rs` (every local slot an instruction addresses; mesh slots untouched).
2. Reload, `crates/shards-core/src/reload.rs` and `stackless/runtime.rs`: `Dep::Inlined` (recorded for the callee and, transitively, for what it inlined; counted by `same_body`, unlike `Dep::Function`), `Retention::{Reuse, Swap, Restart}` replacing the boolean retain test, `swap_body` (cleans up the instance's engine, lays out fresh locals with `Keep` slots carried by name and type, restarts at the next tick), the `swapped` report field, and the admission order in `validate_reload` (functions whose definition changed first, so a rejection names the edited function).
3. `crates/shards-core/src/stackless/engine.rs`, the step: a VM error is handled before any node lookup, since a failed segment may have started at flat control code (the `Const(None)` prelude) that stands for no node. Natively this panicked and was caught, which made the failure look like the one a test expected; on wasm it aborted.
4. `CompiledFunction::inline_depth` and the device bound: unbounded inlining made every level of a chain hold a copy of the code and dependency lists below it (a 24-deep chain's compile peaked 256 against 167 KiB with a counting allocator, exhausting the C3 and the classic ESP32); `INLINE_DEPTH` is 8 on hosts and 2 on ESP-IDF.

Deliberate choices worth challenging: an inlined callee's edit takes effect when the recomposed caller is next entered, not at the callee's next call inside an in-flight caller (a deviation from golden-path §11 for inlined sites, recorded in `docs/current-state.md`; framed callees follow §11 unchanged, pinned by `an_in_flight_parent_selects_the_newest_framed_callee_at_its_next_entry`); a wire whose body inlined a changed function is swapped (iteration in flight cleaned up, `Keep` kept) rather than left running the old code or restarted; hidden slots for a callee's frame are allocated per call site and not cleared between calls (definite assignment makes every read of a callee local follow a write in the same invocation); the inlining budget and depth are constants, not per-function annotations; the callee's own dependencies are not re-propagated on inlining (the call already propagated them; doing it again doubled the lists per level and hung the deep-chain compile).
